# server

LLM router: one OpenAI-compatible endpoint in front of many upstream providers, with virtual keys, budgets and pricing.
Node 24+ (runs `.ts` directly via type stripping), Hono, `node:sqlite`, Zod.

```bash
cp .env.example .env        # fill MASTER_KEY and ADMIN_TOKEN, then export them
vp run server#dev           # or: node src/main.ts
vp test                     # in apps/server
```

## Concepts

|                 |                                                                                                                                                                                                                                                                                                          |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Provider**    | Upstream endpoint (`type: openai-compat`) with a `key_strategy`: `round_robin`, `weighted`, `least_inflight`, `least_used`, `fill_first`, `random`. `sticky_ttl_sec > 0` pins a session (`x-session-id`, `prompt_cache_key` or `user`) to one credential. `headers` are added to every upstream request. |
| **Credential**  | One upstream API key (many per provider; AES-256-GCM at rest). `weight`, `priority`, `models` globs, `rpm_limit`, and `headers` overriding the provider's own per name. 429/5xx -> cooldown with backoff (or `Retry-After`); 401 -> `dead` until the secret is replaced.                                 |
| **Alias**       | Public model name -> ordered `[{provider, model}]`; later targets are fallbacks. `provider/model` also works without an alias.                                                                                                                                                                           |
| **Virtual key** | `sk-pp-…` handed to clients; only its SHA-256 is stored. Optional `allowed_models` globs and `expires_at`.                                                                                                                                                                                               |
| **Limit**       | Per key: `metric` (`usd`, `input_tokens`, `output_tokens`, `total_tokens`, `requests`) x `window` (`30m`, `1h`, `1d`, `7d`, `total`) x `mode` (`fixed` = UTC-aligned, `rolling`).                                                                                                                        |
| **Pricing**     | LiteLLM + OpenRouter synced daily (ETag), manual overrides win. Cost handles cached/reasoning tokens and long-context tiers.                                                                                                                                                                             |

## API

Client: `POST /v1/chat/completions` (JSON or SSE), `GET /v1/models`, `GET /healthz`. Auth: `Authorization: Bearer sk-pp-…`.

Admin (`Authorization: Bearer $ADMIN_TOKEN`):

## Models

Each provider's model list is available from `GET /admin/providers/:id/models` (with `$/1M` prices joined in) and, for clients, as `provider/model` entries in `GET /v1/models` next to the aliases (filtered by the key's `allowed_models`). `GET /admin/models` returns every provider's stored list at once; `PATCH /admin/models/:provider/:model` with `{"enabled": false}` switches a model off: it is no longer routed to (404 `model_not_found`, skipped inside aliases) and leaves `/v1/models`. Any `provider/model` id can be switched, listed or not.

Model entries carry description, created, context window, max output, modalities and supported parameters. The provider's own values win; gaps are filled from OpenRouter's catalog (synced with the pricing, `PRICING_SYNC_ENABLED`) and the admin lists name the catalog per field in `sources`. `GET /v1/models` returns them OpenRouter-style (`context_length`, `architecture`, `pricing` as USD-per-token strings, `top_provider`, `supported_parameters`); add `?verbose=1` for `description`. Facts that are unknown are omitted.

- **OpenAI-compatible and Anthropic providers** are fetched from the upstream (`GET {base_url}/models`, Anthropic paginated) with one of the provider's active credentials, trying up to three. The result is stored in SQLite, so listing never waits on the network and survives restarts. It is fetched on the first view, on `POST …/models/refresh`, at startup and every `MODEL_SYNC_INTERVAL_HOURS` (default 6, `0` = on demand only). A failed refresh keeps the previous list and reports the error. The parser accepts `{data:[…]}`, `{models:[…]}`, bare arrays, string entries and `context_length`/`context_window`.
- **OAuth providers (Kiro, Antigravity)** have a fixed built-in list (`src/providers/kiro/models.ts`, `src/providers/antigravity/models.ts`), because their backends offer no discovery we can call per account. Any other id still works as `provider/<id>`: requests are routed by name whether or not it is listed.

## Account quota (Kiro, Antigravity, Codex)

Subscription accounts have an allowance the upstream reports per account. `GET /admin/providers/:id/quota` (all OAuth accounts of a provider) and `GET /admin/credentials/:id/quota` return it as `windows` (`label`, `used_percent`, `resets_at`), plus `credits` (Kiro) and `exhausted`; `GET /admin/provider-types` marks the types that support it (`quota: true`). The admin UI shows it on the provider page.

- **Kiro**: `AmazonCodeWhispererService.GetUsageLimits` on `management.<region>.kiro.dev` (a canonical `runtime.<region>.kiro.dev` base URL maps to it; any other `base_url` is used as given). The region is the profile ARN's (an enterprise profile can live elsewhere than the runtime region), else `apiRegion`, else `ssoRegion`, else `us-east-1`. The plan allowance is the `AGENTIC_REQUEST` row (else `CREDIT`) as a "Monthly credits" window with fractional credits; a free-trial allowance is its own window. `exhausted` means the allowance is spent **and** overage is disabled. An account without a profile ARN (and not Builder ID) is `account_unavailable`.
- **Antigravity**: `v1internal:retrieveUserQuotaSummary` with the account's project, falling back to `fetchAvailableModels`. Windows are `Gemini 5h`, `Gemini weekly`, `Claude 5h`, `Claude weekly` (Claude includes the third-party models), plus `Argon 5h` / `Argon weekly` for the separate Gemini 4 Argon pool (a bucket's own id/name decides its family, Argon before Gemini; Argon is not read from the fallback), or one `Gemini` / `Claude` meter from the fallback. A full window never sets `exhausted`: the account still serves the other family. A 403 is retried with a plain user agent; the destination is the provider's `base_url`.
- **Caching and probes**: a reading is reused for 10 minutes, a failure for 1 minute; `?refresh=true` probes now. Probes of one account are shared; an expired access token is refreshed (and a 401 refreshed once and retried) like on the request path. Failures are a closed set (`account_unavailable`, `access_denied`, `rate_limited`, `upstream_error`, `timeout`, `transport_error`, `response_unusable`), never upstream text.
- **Parking**: an account found `exhausted` is taken out of rotation until `resets_at` (10 minutes when unknown) and shows as cooling in the credential list; a later reading that is no longer exhausted puts it back. A 429 from an OAuth account triggers a probe (at most one a minute per account) so failover and parking happen on the first sign of a spent quota.
- **Sync**: every account is re-read at startup and every `QUOTA_SYNC_INTERVAL_MINUTES` (default 30, `0` = on demand only). Parking is in memory and rebuilt by that sync after a restart.

## Behaviour worth knowing

- Limits are checked before a request and recorded after it, so concurrent in-flight requests can overshoot by their own cost.
- Streaming: the router adds `stream_options.include_usage`. A stream that ends without a usage chunk (client abort, provider without usage) is logged as `aborted`/`no_usage` with 0 tokens.
- Unknown model price: billed $0 and flagged `price_source=unknown` (`UNPRICED_MODELS=reject` refuses instead). Cooldown state is in memory; `dead` credentials persist.
- Single process by design: counters live in SQLite and pool state in memory.

## Anthropic

**Outbound**: provider type `anthropic` (adapted from [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex), MIT; default `base_url` `https://api.anthropic.com/v1`, credentials are API keys sent as `x-api-key` with `anthropic-version: 2023-06-01`). The router's OpenAI request is translated to `POST {base_url}/messages` and the Messages response/SSE back to chat completions, including `reasoning_content`, tool calls and `cache_control` on content parts, tools and messages.

- `max_tokens` is mandatory upstream: `max_tokens` / `max_completion_tokens`, else 8192 (or the thinking budget + 8192). `temperature`/`top_p` are clamped to 0..1, and dropped where the model rejects them (thinking enabled, Opus 4.7+, Sonnet 5+, Haiku 5.5+); where a model takes only one of them, `top_p` yields to `temperature`.
- Thinking: `thinking` (Anthropic shape) or `reasoning_effort` select it. Models that only accept adaptive thinking (Opus 4.7+, Sonnet 5+, Haiku 5.5+, Fable) get `thinking: adaptive` + `output_config.effort`; older ones get a `budget_tokens` below `max_tokens`. Signed thinking blocks travel in the non-standard `thinking_blocks` field (response and request) so tool loops keep working; without them a manual-budget request drops thinking instead of failing. Switching it off follows each family's contract: `reasoning_effort: "none"` / `thinking: disabled` send `disabled` on Sonnet 5 - 5.4 and Haiku 5.5+, `between_tools` on Sonnet 5.5+ (which rejects `disabled`), and nothing on Opus 5.5 and Fable (which have no off switch) or on models that only think when asked.
- Usage: `prompt_tokens` = `input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens` (OpenAI semantics), so cache reads/writes are priced at their own rates. Reported `output_tokens_details.thinking_tokens` becomes `completion_tokens_details.reasoning_tokens` (a share of `completion_tokens`, not extra).
- Histories OpenAI clients may send but Anthropic rejects are repaired: orphan tool results become text, unanswered tool calls get an error result, and a history that is empty or ends with an assistant turn gets a trailing `(continue)` user turn (newer models reject assistant prefill). Unsupported content (non-http/data image URLs) yields Anthropic's 400 without an upstream call.
- Tool choice: models that refuse forced tool use (Opus 5.5, Fable 5.1+, Sonnet 5.5+) get `auto`; a named choice still narrows the declared tools to that one.
- Structured output: `response_format: {type:"json_schema"}` becomes `output_config.format`, with the schema reduced to what Anthropic accepts (closed objects, `oneOf` as `anyOf`, unsupported constraints folded into the description); a schema without a `type` is a 400. `json_object` has no equivalent and is ignored.
- Responses: `stop_reason: "error"` (forwarded by some compatible upstreams) fails the turn instead of reporting a stop; a stream that closes after its stop reason without `message_stop` still completes; a blank `tool_use` id is replaced by a made-up one; `reasoning` blocks of compatible reasoning models are read like `thinking`.
- Not ported: fast mode (`speed`), automatic prompt-cache breakpoints and the reference's 1-hour default cache TTL for first-party Anthropic (it only rewrites breakpoints the router would add or the native passthrough forwards; the client's own `cache_control`, with its own `ttl` if any, is sent as given), the image re-encoding and image-limit guard, and the managed native-client lane (including its beta-header/body-field pairing). Opus 5.5 keeps `thinking.display: "summarized"`: the reference's `display: "updates"` mode (beta `thinking-display-updates-2026-08-18`, progress updates re-emitted as signed commentary text) has no chat-completions field to carry commentary, so progress updates stay in `reasoning_content`. The reference's rejected-thinking recovery, server-tool replay and Responses refusal verdicts belong to its Responses front end and are not ported: a rejected signature is returned to the client as Anthropic's 400, and `refusal` / `content_filter` end the turn with `finish_reason: "content_filter"`.

**Inbound**: `POST /v1/messages` (JSON or SSE) accepts Anthropic requests (`x-api-key` or `Authorization: Bearer` with a virtual key), so Claude Code and the Anthropic SDKs work against the router: `ANTHROPIC_BASE_URL=http://router:8080 ANTHROPIC_API_KEY=sk-pp-…`. It runs the same pipeline as chat completions (limits, aliases/routing, credential pool, accounting) against **any** provider type, and answers in Anthropic's format with `{type:"error",error:{type,message}}` errors. `top_k` and `thinking` are forwarded to the upstream as extra fields (an OpenAI-compat upstream that rejects unknown fields will 400). Server tools (`web_search_*`, ...) and `count_tokens` are not supported.

## Claude Subscription

Provider type `claude-subscription` ("Claude (Pro/Max)"): Claude models billed to a signed-in **Claude Pro/Max** account instead of an API key. **[can1357/oh-my-pi](https://github.com/can1357/oh-my-pi) (`packages/ai`, `packages/catalog`) is the primary reference** for everything the vendor sees (OAuth, request identity, headers and betas, usage parsing, model discovery); [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex) (MIT) is only the secondary one, for what oh-my-pi does not have (see the list at the end). Where the two differ the provider follows oh-my-pi. It is not an official API for third-party use: the OAuth client and request shape mimic the Claude Code CLI, and Anthropic can change or block that at any time (check the subscription terms before using it for anything but your own work).

```bash
curl -H "$A" -H "$J" localhost:8080/admin/providers -d '{"id":"sub","type":"claude-subscription"}'   # base_url defaults to https://api.anthropic.com/v1
curl -H "$A" -H "$J" localhost:8080/admin/providers/sub/oauth/start -d '{}'                              # -> { session_id, auth_url, ... }
# open auth_url, sign in to Claude; the browser then lands on http://localhost:54545/callback?code=…&state=… which cannot load: that is expected.
curl -H "$A" -H "$J" localhost:8080/admin/oauth/sessions/$SID/complete -d '{"input":"<the full URL from the address bar>"}'
curl -H "authorization: Bearer sk-pp-…" -H "$J" localhost:8080/v1/chat/completions -d '{"model":"sub/claude-sonnet-4-5","messages":[{"role":"user","content":"hi"}]}'
```

- **Wire** (like oh-my-pi): the same Messages translation as the `anthropic` provider (thinking, caching, usage, history repair; see above), sent to `/messages?beta=true` as a Claude Code request. The account's access token is `Authorization: Bearer`; the headers are the CLI's (`User-Agent: claude-cli/<version> (external, cli)`, `x-app`, `anthropic-dangerous-direct-browser-access`, `X-Stainless-*` with the SDK's OS/arch names, `Accept: application/json`, `Accept-Encoding: gzip, deflate, br, zstd`, `Connection: keep-alive`, a per-conversation `X-Claude-Code-Session-Id`; `X-Stainless-Runtime-Version` is pinned to the Node release the CLI reports, not Bun's `process.version`; no per-request id header). The betas follow oh-my-pi's profile by request kind: an **agent** request (it carries tools or asks for thinking) sends `claude-code`, `oauth`, `interleaved-thinking`, `thinking-token-count`, `context-management`, `prompt-caching-scope` and `mid-conversation-system`; any other (**utility**) request sends `oauth`, `interleaved-thinking`, `thinking-token-count`, `context-management`, `prompt-caching-scope` and `structured-outputs`. `effort` is added when the request thinks or the body pins an `output_config.effort`. `context-1m` is never sent (a subscription has no long-context credit; Anthropic answers 429). The request always carries a `tools` array (empty when the client sent none), as an OAuth request of oh-my-pi does. The system prompt starts with two blocks Claude Code sends: a **billing block** `x-anthropic-billing-header: cc_version=<version>.<3-char fingerprint of the first user turn>; cc_entrypoint=cli; cch=<attestation>;` and the identity `You are Claude Code, Anthropic's official CLI for Claude.` (with a 1-hour `cache_control` breakpoint, oh-my-pi's default for OAuth, unless the client already uses all four breakpoints; a client that caches a tool keeps the plain 5-minute one, because the API refuses a 1-hour breakpoint after a shorter one); the client's own system prompt follows. `cch` is the low 20 bits of an XXH64 (seed `0x4d659218e32a3268`) of the exact request bytes with the placeholder in place, as the CLI computes it (our own XXH64, not `Bun.hash`, so it does not depend on the runtime). `metadata.user_id` is the CLI's JSON (`device_id`, `session_id`, `account_uuid`); a client `user` is not forwarded. The router keeps no conversation state, so the session id is derived from the account and the first user turn (stable through a conversation, different between conversations; oh-my-pi uses its agent session id) and the device id from the account (oh-my-pi: from its install id and the account). Without all this Anthropic refuses or flags a subscription token.
- **Version**: the presented Claude Code version is pinned (`DEFAULT_CLI_VERSION`); when Anthropic answers a 4xx naming `claude_code_version_too_old` and a newer minimum, the router adopts that version for the rest of the process and resends the request once (a repeated rejection is returned as is).
- **Tool names**: a subscription token rejects arbitrary tool names, so every client tool is sent as `_<name>` (in definitions, `tool_choice` and the tool calls of the history) and one `_` is removed from the answer, streamed or not. Anthropic's own names (`web_search`, `code_execution`, `text_editor`, `computer`) are left alone. A client tool that already starts with `_` is wrapped too (`__x`), so the round trip is lossless.
- **Login** (like oh-my-pi) is a paste flow (nothing on the router listens on the registered `localhost:54545` redirect). The pasted text may be the full URL, its query string, `code#state` (what Claude's own code page shows) or the bare code; a URL/query must carry the `state` of the login that was started (oh-my-pi's callback server checks it the same way). PKCE (S256), client id `9d1c250a-…` and the authorize URL `https://claude.ai/oauth/authorize?code=true&…` of the CLI, with its six scopes (`org:create_api_key user:profile user:inference user:sessions:claude_code user:mcp_servers user:file_upload`); the code is exchanged as JSON (`grant_type`, `client_id`, `code`, `state`, `redirect_uri`, `code_verifier`) at `https://api.anthropic.com/v1/oauth/token` with only a `Content-Type` header. The token response must carry `access_token`, `refresh_token` and `expires_in`; the access token counts as expired 5 minutes early (oh-my-pi's `skew-ms=300000`, on top of the router's own 60 s refresh margin). The account is labelled with the email of the token response (as sent, not lower-cased); its provider-side id and the organization the token draws limits from are stored (`account_uuid`, `organization_uuid`, `organization_name`). A token response that omits the account, the email or (at sign-in) the organization is completed from Claude Code's `GET /api/claude_cli/bootstrap?entrypoint=cli&model=claude-opus-4-8` (best effort); the organization is fixed at sign-in and a refresh never rewrites it.
- **Refresh** (like oh-my-pi): JSON `grant_type=refresh_token` with the SDK's OAuth headers (`anthropic-beta: oauth-2025-04-20`, `User-Agent: anthropic-sdk-typescript/<version> userOAuthProvider`; the code exchange has neither). A failure is classified by oh-my-pi's rule (`isOAuthExpiry`) on its status and the start of the answer body: `invalid_grant`, `invalid_token`, `unauthorized_client`, `revoked` or "refresh token … expired" retire the account until it signs in again, and so does a bare HTTP 401 unless the text names an outage (timeout, network, 408/425/429/5xx, rate limit, `forbidden`, Cloudflare, captcha…); anything else is transient and only cools it down. The RFC 6749 `invalid_client` and the codes `refresh_token_reused` / `revoked_token` / `refresh_token_revoked` that the earlier opencodex-based rule listed are no longer final on their own (oh-my-pi does not list them). Refresh tokens rotate and are re-stored on every refresh. Unlike the reference there is no background refresh, no cross-process refresh lease and no refresh-intent ledger: tokens are refreshed on demand shortly before expiry, or once after an upstream 401. A Claude grant ends about 30 days after sign-in whatever the rotation; the account then needs a new sign-in (the reference warns before that, the router does not). A token endpoint redirect is never followed (an unknown outcome after a possible rotation, not a refusal; oh-my-pi follows it).
- **Models** (like oh-my-pi's discovery): `GET {base_url}/models` with `Authorization: Bearer`, `anthropic-version`, `anthropic-dangerous-direct-browser-access: true` and the account-route betas (`claude-code`, `oauth`, `interleaved-thinking`, `redact-thinking`, `context-management`, `prompt-caching-scope`, `mid-conversation-system`, `advanced-tool-use`, `effort`, `extended-cache-ttl`), no Claude Code user agent. Unlike oh-my-pi the list is paged to the end (`after_id`) and not merged with a bundled catalog.
- **Quota** (like oh-my-pi's `usage/claude.ts`): `GET {API root of base_url}/api/oauth/usage` (a `/v1` or `/api/oauth` suffix is stripped, a proxy path prefix kept; the CLI's user agent, `Accept-Encoding`, `Connection` and the account-route betas above) gives a `5h` and a `Weekly` window for the account (`five_hour` / `seven_day`, or the `session` / `weekly_all` entries of `limits` when those are missing) plus `Opus weekly` / `Sonnet weekly` (legacy buckets) and `Fable weekly` / `Mythos weekly` (and any of the four) from the `weekly_scoped` entries of `limits`; only those four family labels are ever published (oh-my-pi publishes whatever display name the entry carries). A host answering 404/405/410/501, an empty or non-JSON body, or a body without any usage key is given up on for `https://api.anthropic.com` (the provider's custom headers go to the configured host only). The account is parked until the reset when the 5-hour or the weekly window is spent. A spent family window parks that **model scope** only (`opus`, `sonnet`, `fable`, `mythos`, taken from the model id; `haiku` and others have none), so the account keeps serving its other models. The endpoint is rate limited upstream, so readings are cached like any other (`QUOTA_SYNC_INTERVAL_MINUTES`); there is no in-probe retry loop (oh-my-pi retries up to 3 times and backs off 60 s after a failure; the quota service's cache and cooldown do that here).
- **Rate-limit headers**: every answer, a refusal too, is read for `anthropic-ratelimit-unified-{5h,7d,7d_oi}-{utilization,reset}` (`7d_oi` is the Fable weekly window, as in the reference). Those windows are merged into the cached reading and can park the account (5h or weekly at 100%) or the Fable scope at once, without waiting for the next probe. Headers only park: lifting a park, or a scope's cooldown, needs a full usage reading (a complete one, i.e. with both shared windows, for the cooldown).
- **429s**: for Fable and Mythos a 429 is taken to be the family's own weekly cap and cools the account for that scope only; for Opus, Sonnet and models without a scope it is taken to be a shared wall and cools the whole account, as before (the reference makes the same split). A 429 still triggers a usage probe (at most once a minute per account).
- **Not ported** (omp-agent features or router concerns): the extra-usage / spend limit and banked reset credits of the usage report, the `/profile` identity fallback of the usage probe (identity comes from the token response and the bootstrap), the `fallback-credit` beta and its redemption flow (the beta is not advertised), server-side fallbacks, the experimental-beta kill switch and `PI_AI_CLAUDE_CODE_VERSION`, request compression and connection prewarm, the account pool, usage-ranked credential selection, reserve percentage and session pins, observed-client passthrough lanes (a caller's Claude Code identity, betas and billing preamble), local Claude Code token import, fast mode, the `cache_control`-rejection retry ladder and automatic prompt-cache breakpoints, and image re-encoding. The router's own pool (strategies, sticky key, cooldowns) picks the account.
- **Router-specific or opencodex-only behaviour that remains** (oh-my-pi has no equivalent or cannot be ported): the quota model (parking, per-family model scopes, header readings merged into the cached reading, the Fable/Mythos-local 429 rule), the whitelist of four family labels, the paged model list, no redirect-following on the token endpoint, a login that fails when the token response has no refresh token (oh-my-pi would store an empty one), the conversation/device ids derived from the account (no agent session or install id on a server), and the 60 s on-demand refresh instead of oh-my-pi's background refresh.

## ChatGPT Subscription

Provider type `chatgpt-subscription` ("ChatGPT (Plus/Pro, Codex)"): OpenAI models billed to a signed-in **ChatGPT Plus/Pro/Team** account through the Codex backend, instead of an API key. **The primary reference is [can1357/oh-my-pi](https://github.com/can1357/oh-my-pi) (omp, MIT; `packages/ai` and `packages/catalog` at `3a2758b68`)**: the OAuth client and flow, the Codex identity (originator, version, user agent, headers), the request transformer, the Responses event handling, the error mapping, the usage windows and the model list all follow it, with its KDL rules resolved to their effective values (no rules machinery is ported). [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex) (MIT) is secondary: only the chat-completions side that omp's agent context has no counterpart for (message roles, `response_format`, the shape of the router's `Quota`) and the SSE plumbing come from it. It is not an official API for third-party use: the OAuth client and request shape mimic the omp / Codex CLI, and OpenAI can change or block that at any time (check the plan terms before using it for anything but your own work).

```bash
curl -H "$A" -H "$J" localhost:8080/admin/providers -d '{"id":"codex","type":"chatgpt-subscription"}'   # base_url defaults to https://chatgpt.com/backend-api
curl -H "$A" -H "$J" localhost:8080/admin/providers/codex/oauth/start -d '{}'                         # -> { session_id, auth_url, ... }
# open auth_url, sign in to ChatGPT; the browser then lands on http://localhost:1455/auth/callback?code=…&state=… which cannot load: that is expected.
curl -H "$A" -H "$J" localhost:8080/admin/oauth/sessions/$SID/complete -d '{"input":"<the full URL from the address bar>"}'
curl -H "authorization: Bearer sk-pp-…" -H "$J" localhost:8080/v1/chat/completions -d '{"model":"codex/gpt-5.6-sol","messages":[{"role":"user","content":"hi"}]}'
```

**Like omp**

- **Endpoint**: the default `base_url` is omp's `https://chatgpt.com/backend-api` and the request goes to `POST {base_url}/codex/responses`; a base ending in `/codex` gets `/responses`, one ending in `/codex/responses` is used as is (so an existing `https://chatgpt.com/backend-api/codex` provider keeps working). The account endpoint (`wham/usage`) always lives on the canonical origin (`chatgpt.com` or `chat.openai.com`) directly under `/backend-api`; a `base_url` on any other host is ignored for it.
- **Identity**: `Authorization: Bearer`, `chatgpt-account-id` (the `chatgpt_account_id` claim of the access token, as omp reads it; the stored account id is only used by the quota probe), `OpenAI-Beta: responses=experimental`, `originator: omp`, `version: 0.159.0` (omp's pinned Codex client version; the backend gates which models it serves on it, so bump it with omp), `User-Agent: omp/18.13.2` (omp's `packages/utils` version; pinned in `constants.ts`), `x-codex-routing-hint: model=<id>`, and `x-openai-internal-codex-residency` when the token names a region-pinned workspace (a value the provider's custom headers set wins). The session headers follow the client's `prompt_cache_key` when it sends one (`session_id`, `conversation_id`, `x-client-request-id`; none when it does not, as in omp), plus omp's per-turn metadata: `session-id`, `thread-id`, `x-codex-window-id` and `x-codex-turn-metadata` (and the same fields in the body's `client_metadata`). The thread and window of a session are kept by the router for the session's life (bounded in memory); every request is a new turn. These identity headers override a custom header of the same name; `x-oai-attestation` is never sent (omp only sends it when its host app installs a DeviceCheck provider).
- **Wire**: the chat-completions request becomes a Responses request with `store: false`, `stream: true` (always: a non-streaming client gets the stream aggregated), `include: ["reasoning.encrypted_content"]`, `prompt_cache_key` (kept up to 64 characters, else hashed to `pc_…`, omp's rule), `instructions` = the first system/developer message, the other system/developer messages as `developer` messages in front of the conversation (a conversation of system prompts only asks the last one as a user message), `input` items as omp builds them (user items `{role, content}` with text first then images, `detail` always sent and `auto` by default, blank text dropped; assistant text as `output_text` messages with `status: "completed"`; `function_call`; `function_call_output`), `call_id`s rewritten to `[A-Za-z0-9_-]{1,64}` (a lossy rewrite gets a hash suffix; the same one for a call and its result), unpaired tool exchanges repaired (a result without a call becomes an assistant note truncated at 16 000 characters, a call without a result gets a placeholder output), function `tools` with `strict` only when the tool said so and the schema made Responses-safe (`oneOf` -> `anyOf`, every object schema has `properties`, every array schema has `items` (an open `true` when omitted, as omp's Codex-only repair does it, except next to `unevaluatedItems`), lookaround `pattern`s dropped), `tool_choice` (a named function the request does not offer is dropped), `text.verbosity`.
- **Reasoning**: `reasoning` is sent only with an effort (`reasoning_effort` / `reasoning.effort`), as `{effort, summary}` with `summary` `auto` unless the client says otherwise (`reasoning.summary: null` opts out); `none` sends `{effort: "none"}` alone; `minimal` is clamped to `low` (the models' ladder is `low`..`max`). Without an effort there is no `reasoning` field: the backend's default effort applies and no summaries come back.
- **Not forwarded**: `max_tokens` / `max_completion_tokens`, `temperature`, `top_p`, `stop`, penalties, `seed` and `service_tier` are dropped (the backend refuses sampling controls with 400 "Unsupported parameter", omp sends none either); `n` is ignored.
- **Response**: output text and refusals -> `content`; reasoning summaries (parts separated by a blank line) and raw reasoning text -> `reasoning_content`; function calls -> `tool_calls` by index (a call without parameters gets `{}`); `finish_reason` by the response `status` as omp maps it: `completed` -> `stop` (`tool_calls` when there are calls), `incomplete` -> `length` (promoted to `tool_calls` when `max_output_tokens` cut the answer after every call was complete), `failed` / `cancelled` fail the request; usage from the terminal event (`cached_tokens` or `prompt_cache_hit_tokens`, `cache_write_tokens`, `reasoning_tokens`) in the last chunk. Failures read like omp's: `Codex response failed: <message> (code=…, status=…)` / `Codex error event: …`, and a stream that ends without its terminal event fails with `Codex stream ended before terminal completion event`.
- **Errors** (omp's `parseCodexError`): upstream non-2xx responses keep their status, body and `retry-after`, except that a spent usage limit (`usage_limit_reached` / `usage_not_included`, whatever its HTTP status) is a 429 with code `insufficient_quota` and omp's sentence (`You have hit your ChatGPT usage limit (<plan> plan). Try again in ~N min.`), a rate limit (`rate_limit_exceeded` or any 429 with a JSON body) is a 429 `rate_limit_exceeded` (`ChatGPT rate limit exceeded. Try again in ~N min.`), and the reset becomes `retry-after` when the backend sent none. For a usage limit the reset is `error.resets_at`, else the `x-codex-primary/secondary-reset-at` headers; a rate limit (`turn_rate_limit_exceeded`, "Codex is at capacity") is not the plan window, so only `error.resets_at` or the later reset of a header window that is spent (`used-percent` at 100 or more) counts: a window with headroom never turns a capacity 429 into an hours-long wait, the backend's own `retry-after` stands. An account policy denial (`cyber_policy`, "trusted access for cyber") is returned as a 403 so the gateway tries another account, as omp retries it with a sibling credential.
- **Login**: omp's browser login as a paste flow (nothing on the router listens on the registered `localhost:1455` redirect). PKCE (S256), client id `app_EMoamEEZ73f0CkXaXp7hrann`, scopes `openid profile email offline_access api.connectors.read api.connectors.invoke`, authorize parameters `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, `originator=omp`; the code is exchanged form-encoded (`grant_type`, `client_id`, `code`, `code_verifier`, `redirect_uri`) with a 15 s timeout, and a response without access token, refresh token or `expires_in` is refused. The account is labelled with its email and the workspace id and plan are read from the token claims exactly where omp reads them (`https://api.openai.com/auth`.`chatgpt_account_id` / `chatgpt_plan_type`, `https://api.openai.com/profile`.`email`; access token first, then the id token; nothing from the top level of the payload). A login whose tokens carry neither workspace nor email is refused.
- **Refresh**: form-encoded `grant_type=refresh_token` with the client id. A refresh failure retires the account when omp would treat the grant as dead: the answer's `<status> <body>` matches `invalid_grant|invalid_token|unauthorized_client|revoked|refresh token … expired`, or it is a 401 that does not read like a passing outage; anything else is transient. A refresh keeps the stored refresh token when none is rotated, takes a new email and workspace from the claims, and keeps the plan stored at login (omp does the same).
- **Models**: omp's bundled `openai-codex` chat models: `gpt-6.1-sol` (500k context), `gpt-6-sol`, `gpt-6-luna`, `gpt-6-astra` (272k), `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` (1M, omp's subscription floor), 128k output, text + image input, effort ladder `low`..`max`; plus `gpt-6.1-terra` (500k, paid plans), which omp only discovers live from the Codex backend (its bundle has no row yet) and opencodex's roster lists with that default window. `gpt-5.5` (listed by opencodex, not by omp) is gone from the list; any id still works as `codex/<id>` and is refused upstream when the account cannot use it. The Daybreak cyber programme (`gpt-daybreak-*`, gated by access programs) and `gpt-image-2` (an image tool) are left out. Subscription usage is not billed per token: price the models in the router like any other if you want budgets to count them.
- **Quota**: `GET https://chatgpt.com/backend-api/wham/usage` with `Authorization`, `User-Agent: omp/<version>` and `ChatGPT-Account-Id`. `primary_window` and `secondary_window` are labelled as omp labels them (`5 hours`, `7 days`, `1 hour`, `<n> days`; a window that does not say its length is `Primary window` / `Secondary window`), a `limit_window_seconds` of a day or more rounds to days, else to hours. The Spark meter (`additional_rate_limits` entries naming `spark` or `bengalfox`) is a model scope (`<label> (Spark)`): a spent Spark window stops Spark models only. The account is parked until the reset when it is blocked: the endpoint's verdict (`allowed: false` or `limit_reached: true`) wins, an explicit `allowed: true` outranks a window at 100%, and without a verdict a spent shared window decides. Credits (`has_credits` or `unlimited`, not `overage_limit_reached`, spend control not reached) keep an account that spent its plan allowance serving, but only when the plan verdict says `limit_reached: true` (omp's `hasPlanCreditOverage`) and the per-user spend cap does not say no: a cap with no `reached` verdict whose counters show no headroom (`used` at `limit`, `used_percent` 100, or a bare `remaining` of 0) cannot fund the overage. Credit-billed workspace seats (Business/Enterprise flexible pricing) report no plan windows, only `spend_control.individual_limit`: it is read as a `Spend cap` window (exact fraction from `used`/`limit`, else `used_percent`) and is then the account's meter and verdict (`spend_control.reached` wins in both directions, without it the counters decide); beside plan windows it is shown but never parks. Not ported: omp's per-request gating of the spend cap and its usage-report cache version (the router has no such cache).
- **Rate-limit headers**: every answer, a refusal too, is read for `x-codex-{primary,secondary}-{used-percent,window-minutes,reset-at}` and merged into the cached reading by window label. Headers park only on a refusal: an answer that was served proves the account still works, so its windows are shown but never park.

**Divergences from omp** (deliberate)

- **Models are a fixed list**: omp fetches `/codex/models` per account at run time and the router has no live model listing, so the list is omp's bundled one. `-wm` worker aliases and Daybreak access-program gating are not ported.
- **Instructions**: a stand-in `You are a helpful assistant.` when the client sent no system message (omp always has a system prompt, and the backend refuses a request without `instructions`). A system message in the middle of a conversation is moved in front of it, because omp's context has no such thing.
- **Gateway extras that omp's agent does not have**: `response_format` (`json_object` / `json_schema`) becomes `text.format`; `parallel_tool_calls: false` is forwarded (omp leaves parallelism to the backend); a response cut by the content filter keeps the `content_filter` finish reason; `reasoning_effort: "minimal"` is clamped instead of rejected.
- **Identity state**: the installation id is random per router process (omp keeps one per machine on disk); thread and window ids are kept per `prompt_cache_key` in memory only; no `x-codex-turn-state` / `x-models-etag` stickiness.
- **Schema**: omp's draft-07 -> 2020-12 upgrade and strict-mode enforcement (`adaptSchemaForStrict`) are not ported: a client's `strict: true` is forwarded as is. Harmony control-token escaping is not needed (omp applies it to `gpt-oss`-class models only). Hash values (`pc_…`, call-id suffixes) use SHA-256 where omp uses `Bun.hash`: they are opaque on the wire.
- **Usage accounting**: the backend's orchestration token counters (`orchestration_*`) are not read; `total_tokens` is prompt + completion.
- **Login**: paste flow only; omp's device-code login (`auth.openai.com/api/accounts/deviceauth/*`) is not ported because a provider type has one login flow in the router.
- **Not ported** (omp-agent or gateway-excluded): the Responses front end for Codex clients, the account pool, leases and credential selection (quota rank, reserve, plan gates), fast mode / service tier and ultrafast, automatic prompt-cache keys and retention, image resizing, zstd request bodies, the WebSocket transport, remote compaction, prewarm and live steering, the Responses Lite contract, cyber access programs ("Daybreak") and attestation, retries (the router's pool, cooldowns and failover cover them), reasoning-item replay, reset-credit redemption, verified-access lookup, and the stable-effort `configuration_update` mechanism of the GPT-6 family. The router's own pool (strategies, sticky key, cooldowns) picks the account.

## Antigravity

Provider type `antigravity` ("Google Antigravity"): Gemini, Claude and gpt-oss models through Google's Cloud Code Assist backend (`v1internal`), billed to the signed-in Google account's Antigravity subscription. Ported from [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex) (MIT). It is not an official API: the OAuth client and request shape mimic the Antigravity desktop IDE, and Google can change or block that at any time.

```bash
curl -H "$A" -H "$J" localhost:8080/admin/providers -d '{"id":"agy","type":"antigravity"}'   # base_url defaults to https://daily-cloudcode-pa.googleapis.com
curl -H "$A" -H "$J" localhost:8080/admin/providers/agy/oauth/start -d '{}'                   # -> { session_id, auth_url, ... }
# open auth_url, sign in; the browser then lands on http://127.0.0.1:51121/callback?code=…&state=… which cannot load: that is expected.
curl -H "$A" -H "$J" localhost:8080/admin/oauth/sessions/$SID/complete -d '{"input":"<the full URL from the address bar>"}'
curl -H "authorization: Bearer sk-pp-…" -H "$J" localhost:8080/v1/chat/completions -d '{"model":"agy/gemini-3.8-flash","messages":[{"role":"user","content":"hi"}]}'
```

- **Login** is a paste flow (the router is remote, so nothing listens on the registered `127.0.0.1:51121` redirect). The pasted text may be the full URL, its query string, `code#state` or the bare code; a URL/query must carry the `state` of the login that was started, otherwise it is refused and the session stays pending. PKCE (S256) is used, with the six scopes of the 2.26.0 client (`cloud-platform`, `userinfo.email`, `userinfo.profile`, `cclog`, `experimentsandconfigs`, `aicode`; oh-my-pi added `aicode`, the reference does not send it; accounts already signed in keep their tokens). After the code exchange the Cloud Code Assist project is discovered (`loadCodeAssist`, then `onboardUser` with the free tier); an account without a project is refused. The project id is stored with the account (`project_id`).
- **Refresh**: `invalid_grant` / `invalid_client` / `unauthorized_client` retire the account until it signs in again; anything else (5xx, 429, network, other 4xx) is transient and only cools it down.
- **Models**: the upstream model name is mapped like the reference: `gemini-3.8-flash`, `gemini-4-argon`, `claude-opus-5-5`, `claude-sonnet-5-5` (Gemini 4 Argon and Claude 5.5 take `-low|-medium|-high` wire suffixes, default medium; Argon is served only to AI Ultra/Enterprise accounts and, unlike every other model, is sent with the Antigravity CLI User-Agent `antigravity/cli/1.3.4 (...)`, which `GOOGLE_ANTIGRAVITY_USER_AGENT` does not override), `gemini-3.7-flash`, `gemini-3.1-pro`, `gemini-3.1-flash-image`, `claude-sonnet-4-6`, `claude-opus-4-6-thinking`, `gpt-oss-120b-medium`, plus wire ids/aliases (`gemini-pro-agent`, `gemini-3.8-flash-high`, retired `gemini-3.6-flash*` -> 3.7). The fixed list carries the context window (`maxTokens` of the backend's model rows: 1,048,576 Gemini, 250,000 Claude, 131,072 gpt-oss), the input modalities the adapter can carry (text and images; text only for gpt-oss) and the documented output ceiling. The reference's live `:fetchAvailableModels` discovery overlay (extra ids, collapsing `-low/-medium/-high` families into one row) is not ported. `reasoning_effort` (`low|medium|high`; `xhigh`/`max` clamp to `high`) selects the effort wire id or `thinkingLevel`; unknown ids are sent as-is. When the client sends `reasoning_effort` (other than `none`) to a Gemini model, thought summaries are requested and returned as `reasoning_content`. Divergence: upstream trimmed its picker to 3.8 Flash, 4 Argon and the 5.5 models because the 3.7 Flash and 3.1 Pro wire ids 404 live (2026-10-14); this list keeps the older entries and adds the new ones.
- **Request mapping**: system/developer messages -> `systemInstruction`; images / `input_audio` / `file` data URLs -> `inline_data` (remote image URLs become a text marker); tools -> function declarations with schemas reduced to the subset Google accepts (`$ref` inlined, `anyOf` normalised, unsupported keywords dropped, tool names rewritten to Google-legal ones and mapped back); `tool_choice`, `stop`, `max_(completion_)tokens`, `temperature`, `top_p` and `response_format` (Gemini only) are honoured. Tool results are regrouped after their call; a history that opens on a tool call or ends on a model turn gets a `(continue)` user turn.
- **Usage**: Google reports `promptTokenCount` including cached tokens and `candidatesTokenCount` excluding thinking tokens. They are converted to OpenAI semantics: `prompt_tokens` includes cached (`cached_tokens` is the cached part), `completion_tokens` = candidates + thoughts (`reasoning_tokens` is the thoughts part).
- **Thought signatures**: Gemini 3 needs the `thoughtSignature` of a function call echoed back. OpenAI clients cannot carry it, so it is remembered in memory (per model + session derived from the first user message, keyed by call name + arguments, 1 h TTL) and re-injected when the same call appears in the history; otherwise the first call of a turn gets Google's documented bypass token. A restart forgets the signatures.
- **Progress text history (Gemini)**: Gemini sometimes plans in visible text on a tool-calling turn ("Reading the file. Let's read google.ts next."), and replaying that whole turn teaches it to repeat the pattern for the rest of the session. Like the reference, an assistant turn **with tool calls** in the history is therefore replayed to a Gemini model as the lead sentence of its text (first sentence end: `.`/`!`/`?` before whitespace, a script's own terminator, or a line break; list markers and `e.g.`/`i.e.`/`etc.`/`vs.` do not end it; text with no boundary is kept whole). Facts stated only in later sentences of that text are not replayed. Turns without tool calls, Claude and gpt-oss models, tool calls, and the response sent to the client are unchanged. The reference also keeps text after a tool call and Responses `final_answer` turns whole; chat-completions history has neither.
- **Errors**: upstream non-2xx responses are returned unchanged (status, body, `retry-after`), so 401 -> refresh once, 403/429/5xx -> cooldown/failover as for any provider. The one exception is a 400 whose message blames the tool schemas (`input_schema`, `function declarations`, ...) or the thinking config: the call is replayed once with the thinking config dropped and the rejected tool declaration (the one the error indexes, else all of them) opened to a plain object schema, like the reference's Vertex/Antigravity repair; the replay's answer is final. A turn cut off by `MAX_TOKENS` mid tool call, `MALFORMED_FUNCTION_CALL`, or a stream with no terminal frame fails (a stream shows an `error` event) instead of looking complete, and so does a non-stream answer without any candidate. An in-band `error` frame (a stream's final JSON event) keeps the RPC `status` and `details` in its message (`message (STATUS) {...}`, details capped), like oh-my-pi, so a quota or capacity failure stays distinguishable from an outage; oh-my-pi's classification of those details (QuotaFailure / RetryInfo / `MODEL_CAPACITY_EXHAUSTED`) into rotate-or-back-off verdicts is not ported (the gateway classifies by HTTP status). Google's `RetryInfo` hints are not translated into `retry-after`; the reference's own transient-5xx/429 retries and its normalised error messages are not ported (the gateway's cooldown/failover covers them), nor is its quarantine of `VALIDATION_REQUIRED` 403 accounts.
- **Not ported from oh-my-pi's 2.26.0 (`antigravity/hub`) alignment**: this adapter keeps the reference's IDE (`antigravity/ide/2.5.5`) and CLI (Argon) fingerprints and its stateless request envelope (`requestType: "agent"`, `requestId: agent-<uuid>`). oh-my-pi's hub client additionally sends request labels (`cascade_id`, `request_id`, `model_enum`, ...), per-conversation step numbering, per-SKU `maxOutputTokens`/thinking settings read from the account's live `fetchAvailableModels` roster, `Accept-Encoding: gzip` and omits `requestType`; those need session state or live model discovery, which the fixed model list does not have.
- **Environment** (optional overrides, read at start): `GOOGLE_ANTIGRAVITY_CLIENT_ID`, `GOOGLE_ANTIGRAVITY_CLIENT_SECRET`, `GOOGLE_ANTIGRAVITY_USER_AGENT`. All constants live in `src/providers/antigravity/constants.ts`.

## Kiro

Provider type `kiro`: Claude, GPT, DeepSeek, GLM, Qwen and MiniMax models through Kiro's CodeWhisperer streaming API (`AmazonCodeWhispererStreamingService.GenerateAssistantResponse`), billed to the signed-in Kiro / AWS Builder ID account. Ported from [lidge-jun/opencodex](https://github.com/lidge-jun/opencodex) (MIT). It is not a public API: the headers and request shape mimic the Kiro CLI / IDE, and Kiro can change or block that at any time.

```bash
curl -H "$A" -H "$J" localhost:8080/admin/providers -d '{"id":"kiro","type":"kiro"}'   # base_url defaults to https://runtime.us-east-1.kiro.dev
curl -H "$A" -H "$J" localhost:8080/admin/providers/kiro/oauth/start -d '{}'            # -> { session_id, user_code, verification_uri(_complete), ... }
# open verification_uri_complete in any browser, sign in with AWS Builder ID, approve; poll until status is "complete":
curl -H "$A" localhost:8080/admin/oauth/sessions/$SID
curl -H "authorization: Bearer sk-pp-…" -H "$J" localhost:8080/v1/chat/completions -d '{"model":"kiro/claude-sonnet-4.5","messages":[{"role":"user","content":"hi"}]}'
```

- **Login** is a device flow (a remote admin only needs a browser): a public SSO OIDC client `kiro-cli` is registered at `oidc.us-east-1.amazonaws.com`, a device grant is started for `https://view.awsapps.com/start`, and the router polls `/token` at the interval the IdP asks for (`slow_down` is honoured; IdP 5xx and network blips keep the login pending until the code expires, at most 15 min). `expired_token` and `access_denied` end it with an error. Stored with the account (`extra`): `authType=aws_sso_oidc`, the client registration (`clientId`, `clientSecret`), `ssoRegion` and `apiRegion` (both `us-east-1`). The contract allows one login flow per provider type, so the Google / GitHub social device logins, importing a local `kiro-cli` database and pasting tokens are not offered; a Kiro API key (`ksk_…`) can still be added as a normal API-key credential, and an account stored without a client registration is refreshed on Kiro's own endpoint.
- **Refresh** (`refresh_token`): with a client registration `POST https://oidc.<ssoRegion>.amazonaws.com/token` `{grantType:"refresh_token", clientId, clientSecret, refreshToken}`; without one `POST https://prod.<ssoRegion>.auth.desktop.kiro.dev/refreshToken` `{refreshToken}`. HTTP 400/401 with `invalid_grant`, `refresh_token_reused`, `revoked`, `revoked_token`, `refresh_token_revoked`, `access_denied` or `expired_token` retires the account until it signs in again, as does (desktop endpoint only, never the SSO OIDC refresh) the exact pair HTTP 401 + a bare `{"message":"Bad credentials"}` body, surfaced under the fixed code `bad_credentials`; anything else (5xx, 429, network, unknown 4xx, other 401 messages) is transient and only cools it down. A rotated refresh token is persisted; error bodies are never echoed.
- **Regions**: the runtime region is `apiRegion`, else the region in the profile ARN, else `ssoRegion`, else `us-east-1`. A canonical `runtime.<region>.kiro.dev` `base_url` follows it; any other `base_url` (proxy, test double) is used as given. When the canonical host cannot be resolved/reached, answers 404/405/502/503/504, or a 400/403 names an unknown operation/signature, the same call is retried once on the older `q.<region>.amazonaws.com` host.
- **Request mapping** (`src/providers/kiro/request.ts`): leading `system`/`developer` messages become a prompt prefixed to the first user message (Kiro has no system role); later ones are folded into the surrounding user turn. History is rebuilt as strictly alternating user/assistant turns (adjacent same-role messages merged, an opening assistant turn or a trailing assistant turn gets a continuation user turn), assistant `tool_calls` become `toolUses` (objects, ids sanitised to `[A-Za-z0-9_-]{1,64}`) and `tool` messages become `toolResults` (empty output becomes a sentence; an orphaned result, a duplicate id or an unanswered call is a 400). Tools become `toolSpecification`s with the schema subset Kiro accepts (rejected keywords dropped, root `oneOf/anyOf/allOf` flattened, names rewritten to legal unique ones and mapped back on the response, descriptions cut to 1024 chars, at most 48 tools / 96 kB, the omitted ones named in the prompt). Data-URL images are sent inline (max 20 per message, 100 per request; the oldest are dropped with a note); remote image URLs become a text marker. The model id is normalised (`kiro-claude-sonnet-4-5` -> `claude-sonnet-4.5`, `kiro-auto` -> `auto`, date/effort suffixes dropped). `reasoning_effort` (or `reasoning.effort`) is sent natively for `gpt-5.6-*`, `gpt-6*` and `claude-opus-5*` (`additionalModelRequestFields`), for every other model it becomes `<thinking_mode>` instructions budgeted from `max_tokens`, and the model's leading `<thinking>` block is returned as `reasoning_content`. Not expressible, so answered with HTTP 400 and no upstream call: `tool_choice` other than `auto`/`none`, `service_tier`, `response_format` other than `text`, `file`/`input_audio`/`video_url` parts. `temperature`, `top_p`, `max_tokens` and `stop` are not sent (the wire has no field for them).
- **Request shape**: accounts with their own profile ARN use the IDE request shape (`x-amzn-kiro-profile-arn`, `origin: AI_EDITOR`); Builder ID accounts (no ARN of their own) and `ksk_` API keys use the CLI shape (`origin: KIRO_CLI`, `agentTaskType: vibe`), Builder ID carrying Kiro's fixed service profile ARN. Every request gets a fresh `conversationId`: the router holds no Kiro conversation state.
- **Response**: the service only streams an AWS binary event-stream (`application/vnd.amazon.eventstream`). `src/providers/kiro/eventstream.ts` decodes it frame by frame across arbitrary chunk boundaries, verifying the prelude and message CRC32 (a bad CRC, a corrupt length or a stream cut mid-frame fails the response). Text, reasoning and tool calls map to OpenAI chunks; a tool call is emitted whole once Kiro marks it stopped and only if its JSON input is complete. Non-streaming clients get the same chunks aggregated. Stop reasons map to `finish_reason` (`MAX_TOKENS` -> `length`, `CONTENT_FILTERED`/`GUARDRAIL_INTERVENED` -> `content_filter`, a tool call -> `tool_calls`); `MODEL_CONTEXT_WINDOW_EXCEEDED`, exception/error frames, protocol violations and an empty stream fail the request (an SSE `error` event once streaming, a failed attempt for non-streaming).
- **Usage**: when the stream carries `metadataEvent.tokenUsage` it is used as reported: `prompt_tokens` = uncached + cache-read + cache-write input tokens (`cached_tokens`, `cache_write_tokens` are the cache parts) and `completion_tokens` = output tokens. Kiro often reports no token counts (only a `contextUsageEvent` percentage and `meteringEvent` credits, neither of which is converted), so otherwise the reference's heuristic is used: prompt tokens estimated from the whole built request (history, tools, tool results, images; latin text 2.8 chars/token x 1.2 wire expansion, CJK 1.5 chars/token, 27 tokens of framing per turn, an image about 1 token per 750 pixels read from its PNG/JPEG/GIF/WebP header with a floor of 256, or a guess from its encoded size when the header is unreadable) and output tokens from the generated text, reasoning and tool arguments. Estimates err high and are not flagged in the response, so budgets on Kiro accounts are approximate.
- **Errors**: upstream non-2xx is returned with its status in the OpenAI error envelope, so 401 -> refresh once, 403/429/5xx -> cooldown/failover as for any provider; `retry-after` is kept. A 400/429 `MONTHLY_REQUEST_COUNT` (spent monthly quota) or `OVERAGE_REQUEST_LIMIT_EXCEEDED` (exhausted overage allowance) is reported as 429 `insufficient_quota` so the pool rotates to another account (a quota worded as a per-minute ceiling stays a rate limit), a 400 naming an expired/invalid token or access denial (AWS JSON APIs report those as 400) as 401, `CONTENT_LENGTH_EXCEEDS_THRESHOLD` as `context_length_exceeded`, and 5xx bodies are replaced by a generic message. A 403 `TEMPORARILY_SUSPENDED` keeps its status and is named "Kiro account suspended".
- **Not ported from the reference** (they exist for opencodex's Codex/Responses front end or local-machine integration): the private "final answer" completion tool and text-fallback retry, Responses continuations, reasoning-blob replay (`signature` / `redactedContent` are dropped), per-conversation token calibration, image re-encoding and its byte budget, the process-wide 429 throttle gate and connection-reset retries (the gateway's failover covers them), reading/rotating the local `kiro-cli` database, per-account model discovery (`ListAvailableModels`, which upstream only uses as routing evidence), account leases and failover, and the opencodex pieces around usage limits (routing by quota rank, persisting verdicts to disk, passive observation of response headers, the pinned outbound transport for quota probes).
